# Ordo — как разместить в облаке бесплатно и без карты

Дата: **2026-11-25**. Задача: запустить Ordo не на своём компьютере, а в
интернете, **бесплатно** и **без привязки банковской карты**.

Короткий ответ:

- **Минимум переделок и максимальная надёжность → GitHub Actions как «сервер»**
  (код на Python выполняется как есть, `ordo remind` крутится по расписанию,
  состояние — `ordo.db` — коммитится обратно в репозиторий, дашборд — GitHub Pages).
- **Настоящее всегда-доступное веб-приложение → Cloudflare Workers (Python) + D1 +
  Cron Triggers** (код почти как есть, но `sqlite3` надо заменить на D1).

Оба варианта — без карты. Ниже разбор почему и как.

---

## 1. Что именно нужно «разместить»

Ordo — это не статический сайт. Чтобы он жил в облаке, нужно четыре вещи:

1. **Постоянное хранилище.** Задачи/история/напоминания лежат в SQLite-файле
   `ordo.db`. Он должен переживать перезапуск и быть один на всех.
2. **Планировщик.** `ordo remind` надо вызывать регулярно (cron). Фонового
   демона нет — это осознанное решение проекта.
3. **Выход в интернет.** Telegram (`urllib`) или SMTP (`smtplib`).
4. **Секреты.** Токен бота / пароль ящика.

Плюс, по желанию, **интерфейс** — что-то, куда можно посмотреть и что-то
добавить с телефона/чужого компьютера, а не только из локального терминала.

Любое решение должно дать все эти четыре вещи, иначе оно бесполезно.

---

## 2. Ключевые особенности Ordo, влияющие на выбор

- **Чистый stdlib, Python 3.9+.** Нет зависимостей — значит, хостинг нужен
  именно «Python + запуск команды», либо полный порт на другой язык.
- **Состояние — файл SQLite.** Serverless-платформы (Vercel, Netlify, Deno,
  Cloudflare Workers) **не дают** обычного диска. Значит, файл `ordo.db` там
  некуда положить: нужна managed-БД (D1/libSQL/Postgres) и переписанный слой
  `db.py`.
- **Напоминания — команда, а не демон.** Это подходит под cron/GitHub Actions/
  Cron Triggers и **не** подходит под «веб-хук по событию».
- **Telegram и почта — на stdlib.** Telegram работает почти везде (обычный
  HTTPS). SMTP требует «сырых» сокетов и часто недоступен на serverless —
  Telegram надёжнее.
- **CLI-вывод.** Готового веб-интерфейса нет, есть `--json`. Значит, дашборд
  можно сгенерировать из JSON, но интерактив придётся добавлять.

## 4. Вариант A (рекомендуемый): GitHub Actions как сервер

### Идея

GitHub Actions — это бесплатные Linux-раннеры с **настоящим Python**, где уже
лежит код. Используем их как «сервер без сервера»:

- Репозиторий = и код, и **состояние** (`ordo.db` коммитится обратно).
- `.github/workflows/remind.yml` по расписанию запускает `python3 -m ordo remind`.
- Секреты (токен Telegram) — в *Settings → Secrets and variables → Actions*.
- Дашборд: отдельный workflow гоняет `ordo list --json` и публикует `index.html`
  на **GitHub Pages** (только чтение).
- Управление без терминала: issue-команды (`/add ...`, `/done 3`) через
  event `issues` — это паттерн «IssueOps». Бот коммитит БД и отвечает в issue.

### Почему это лучшее «бесплатно и без карты» для Ordo

- **Ноль изменений в бизнес-логике.** `service.py`, `reminders.py`, `cli.py`
  работают как есть.
- **Не нужен диск** — его роль играет git.
- **Public-репозиторий → безлимитные минуты Actions** (приватный — 2000 мин/мес,
  чего хватает при запуске раз в 30–60 мин).
- Телеграм работает: у раннеров полноценный интернет.

### Файлы

- `.github/workflows/remind.yml` — запуск напоминаний (пример ниже).
- `.github/workflows/dashboard.yml` — сборка `index.html` и деплой на Pages.
- `.github/workflows/issueops.yml` — команды из issue (опционально).
- `.github/workflows/bot.yml` — приём команд Telegram-бота (опционально).

### Telegram-бот из Actions

Telegram не умеет «толкать» апдейты на раннер GitHub, поэтому бот **опрашивает**
`getUpdates` (`.github/workflows/bot.yml`, раз в 5 минут — минимум для cron
GitHub). Задержка ответа — до одного интервала, зато без сервера и карты.

```yaml
- name: Answer pending Telegram updates
  env:
    ORDO_DB: ordo.db
    ORDO_TELEGRAM_TOKEN: ${{ secrets.ORDO_TELEGRAM_TOKEN }}
    ORDO_TELEGRAM_CHAT: ${{ secrets.ORDO_TELEGRAM_CHAT }}
  run: python3 -m ordo bot --once
```

`ORDO_TELEGRAM_CHAT` здесь ещё и allowlist: сообщения из других чатов
игнорируются. Обработанное смещение лежит в `ordo.db` (`meta`), поэтому один и
тот же апдейт не обрабатывается дважды; состояние коммитится в ветку `state`
тем же шаблоном, что и в `remind.yml`.

**Как проверить, не дожидаясь cron:** локально

```bash
export ORDO_TELEGRAM_TOKEN="..."
export ORDO_TELEGRAM_CHAT="..."
ordo bot --test      # придёт проверочное сообщение -> токен и чат верные
ordo bot --follow    # живой диалог: пиши /start, /list, /add ...
```

### Пример `remind.yml`

```yaml
name: ordo remind
on:
  schedule:
    - cron: "*/30 * * * *"      # каждые 30 минут (минимум у GitHub — 5 минут)
  workflow_dispatch:            # и вручную кнопкой
concurrency:
  group: ordo-state             # не запускать два раза одновременно
  cancel-in-progress: false
permissions:
  contents: write               # нужно, чтобы закоммитить ordo.db назад
jobs:
  remind:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 1) восстановить состояние (БД) из ветки state, если она есть
      - name: restore db
        run: |
          git fetch origin state || true
          git checkout origin/state -- ordo.db 2>/dev/null || true

      # 2) отправить напоминания (Telegram-токен — из секретов)
      - name: run ordo remind
        env:
          ORDO_DB: ordo.db
          ORDO_NOTIFY: telegram
          ORDO_TELEGRAM_TOKEN: ${{ secrets.ORDO_TELEGRAM_TOKEN }}
          ORDO_TELEGRAM_CHAT: ${{ secrets.ORDO_TELEGRAM_CHAT }}
        run: python3 -m ordo remind

      # 3) сохранить состояние обратно в ветку state
      - name: save db
        run: |
          git config user.name  "ordo-bot"
          git config user.email "ordo-bot@users.noreply.github.com"
          git checkout -B state
          git add -f ordo.db
          git commit -m "state: $(date -u +%FT%TZ)" || exit 0
          git push -f origin state
```

### Схема хранения состояния (выбрать одну)

| Способ | Плюсы | Минусы |
|---|---|---|
| Коммитить `ordo.db` в ветку `state` (как выше) | просто, состояние одно | бинарник в git |
| Коммитить прямо в `main` | ещё проще | шумная история, конфликты |
| Release asset `ordo.db` под фиксированным тегом | чистая история | лишний код в workflow |
| `actions/cache` | быстро | кэш периодически вытесняется, не durable |

Для личного инструмента ветка `state` — оптимум.

### Нюансы, о которых надо знать

- **Расписание «best effort».** GitHub может задержать запуск на 5–20 минут и
  иногда пропустить. Для напоминаний о дедлайнах это нормально.
- **Автоотключение через 60 дней.** В публичных репозиториях scheduled workflow
  отключается, если 60 дней нет активности. У нас как раз есть коммиты БД и
  heartbeat — это держит репозиторий активным. На всякий случай стоит добавить
  «keepalive»-шаг, который раз в неделю делает пустой коммит.
- **Atomic-сохранение.** `concurrency: group: ordo-state` не даёт двум прогонам
  затереть друг друга. Для одного пользователя этого достаточно.
- **Порядок коммита.** Сначала `remind`, потом `save db` — иначе отправим по
  старому состоянию.
- **SMTP лучше не использовать** — Telegram проще и надёжнее.

### Управление из issue (опционально, «IssueOps»)

`issueops.yml` на событие `issues`/`issue_comment` парсит текст (`/add "..." -d 3d`,
`/done 4`, `/comment 4 ...`), выполняет нужную `ordo`-команду, коммитит БД и
отвечает комментарием. Это даёт мобильный интерфейс без сервера и с историей
правок. Ограничение: обработка не мгновенная (десятки секунд на старт раннера).

## 5. Вариант B: Cloudflare Workers (Python) + D1 + Cron Triggers

### Что нового в 2026

С 2026 года **Python Workers вышли в GA** — это CPython (Pyodide, by default
3.14) в WebAssembly. Значит, код Ordo на Python в основном переносится. Работает
на бесплатном плане, **карта не нужна**. Есть **Cron Triggers** (минимум 1 мин,
до 5 на аккаунт) и **D1** — управляемый SQLite (5 ГБ, 5 млн чтений/сутки,
100 тыс. записей/сутки бесплатно).

### Идея

- `fetch()` — отдаёт HTML-дашборд и JSON API (задачи, комментарии, переносы).
- `scheduled()` — аналог `ordo remind`, шлёт напоминания в Telegram.
- Хранилище — **D1** (SQLite), схема из `db.py` переносится почти 1:1.
- Статика (CSS/JS дашборда) — через Workers static assets / Pages, бесплатно.

### Что придётся переделать

| Модуль | Что меняется |
|---|---|
| `db.py` | убрать `sqlite3`/`Path`/WAL; вместо них — binding `env.DB` (D1). Адаптер `.execute().fetchone()/fetchall()` можно сделать тонким, но он асинхронный. |
| `config.py` | брать значения из `env`/секретов Worker, а не из `~/.config` и файлов. |
| `notify/email.py` | SMTP недоступен (нет сырых сокетов) — оставить Telegram. |
| `notify/telegram.py` | отправку `urllib` заменить на `fetch()`, если `urllib` не проксируется. |
| `service.py`, `reminders.py`, `timeparse.py`, `models.py`, `report.py` | логика переносится почти без изменений. |
| новое | `worker.py` с `fetch`/`scheduled` и статикой дашборда. |

`threading`/`multiprocessing` на Workers не работают — Ordo их и не использует,
так что это не проблема.

### Лимиты, о которых помнить

- **CPU на бесплатном плане — 10 мс на запрос.** Для интерактивных страниц на
  Pyodide это впритык; проверяйте реальные цифры. У Cron при интервале ≥ 1 ч
  лимит заметно больше (порядка минут — уточняйте в актуальной документации).
- D1: 5 млн строк-чтений и 100 тыс. строк-записей в сутки — для личного
  планировщика с огромным запасом.
- Cron Trigger минимум — 1 минута (у GitHub Actions — 5).

### Шаги (кратко)

1. `npm create cloudflare@latest ordo -- --type=hello-world` (или Wrangler вручную).
2. `wrangler d1 create ordo` → прописать binding `DB` в `wrangler.toml`.
3. Загрузить схему из `db.py` в D1 (`wrangler d1 execute ordo --file=schema.sql`).
4. Перенести `ordo/*.py`, заменить `db.py` и `config.py`, добавить `worker.py`.
5. Секреты: `wrangler secret put ORDO_TELEGRAM_TOKEN` и `..._CHAT`.
6. В `wrangler.toml` добавить `[triggers] crons = ["*/30 * * * *"]`.
7. `wrangler deploy`.

## 6. Вариант C: только дашборд (если лень переделывать)

GitHub Pages отдаёт статику. Можно генерировать `index.html` из
`ordo list/show --json` и публиковать. Это **не** запускает Python и не шлёт
напоминания — только показывает. Годится как «витрина» поверх Варианта A.

Полноценно «Ordo в браузере без сервера» делается так: перенести логику на JS,
хранить данные в IndexedDB/`sql.js`, а напоминания отправлять… только пока
вкладка открыта (Service Worker не гарантирует фон). Для дедлайнов это плохо,
поэтому такой путь — скорее компромисс, чем решение.

## 7. Вариант D: Val Town / Turso (если готовы на JS)

- **Val Town** — бесплатно, без карты, встроенный SQLite-KV, cron и HTTP-эндпоинты.
  Но это **TypeScript/Deno**, нужен порт логики на JS (аналогичный Варианту B по
  объёму, но ещё и сменой языка). Turso даёт бесплатный libSQL (SQLite), тоже
  без карты, если захотите оставить SQL-модель.

---

## 8. Почему остальное не подходит

- **PythonAnywhere free** раньше был идеален, но с 2026 года у новых бесплатных
  аккаунтов **нет scheduled tasks и нет MySQL**, веб-приложение протухает через
  месяц, а исходящий интернет ограничен белым списком. Как основной хостинг —
  уже нет.
- **Vercel / Netlify / Deno Deploy** — нет постоянного диска; Deno Deploy вообще
  закрывается. Понадобится внешняя БД (Turso) и порт.
- **Render / Fly.io / Railway** — бесплатные тарифы либо спят, либо требуют
  карту. В список «без карты» не берём.
- **GitHub Pages как хостинг самого Ordo** — не запускает Python. Только статика.

---

## 9. Рекомендация

1. Если цель — **чтобы напоминания просто работали, с минимумом возни**:
   **Вариант A (GitHub Actions + Pages)**. Код не меняется, карта не нужна,
   Telegram подключается за 10 минут.
2. Если цель — **настоящее веб-приложение Ordo в браузере**:
   **Вариант B (Cloudflare Workers + D1)**. Больше работы, но получается
   «продукт», а не «скрипт по расписанию».

Хорошая стратегия — начать с A (быстрый результат, напоминания уже работают), а
веб-интерфейс позже сделать на B, переиспользуя те же `service.py`/`reminders.py`.
